# bab as the permission authority: requests, grants with expiry, one-hour leases

2026-10-27 · Kai, for Kyle's team · status: PROPOSAL (increment two and up)

> **Design record.** Follows [design.md](design.md) (increment one, built).
> This document changes bab's role: from a yes/no store the runtime asks at
> tool dispatch to the one place an agent's permissions are requested,
> approved, recorded, leased and audited. Nothing here is code yet.

## Why the change

Increment one answers "may this agent run this tool on this object?" and
leaves credentials to someone else. Two things made that too small.

1. Credentials were the permissions. A vendor key mounted into an agent, or
   a gateway grant file, was a standing permission with no owner, no expiry
   and no record of why it existed. Revoking it meant a deploy.
2. Every vendor had its own grain. A monitoring vendor is "read or write on
   one tool list"; a cloud account is hundreds of services, case by case.
   One row per agent per vendor could not say what an agent may do.

The rule from here: **no agent holds a standing credential. It holds
approved permissions in bab, and borrows a credential for an hour when a
task needs one.**

## Shape

```
owner picks permissions ──► review queue ──► grant (expires) ──► lease (1 h) ──► vendor
     at creation           admins/security    OpenFGA tuple       minted by bab   enforces
```

| Word | Meaning |
|---|---|
| **permission** | one entry in an integration's catalogue: `datadog.monitors.read`, `aws.ec2.describe`, `github.pulls.write`. Tier read, mutate or destroy. |
| **request** | the set of permissions an agent's owner asked for, per integration. Pending until decided. |
| **grant** | an approved request. One conditional tuple per permission, with an expiry. The ceiling check runs at write time. |
| **lease** | a short-lived vendor credential bab mints when a task needs the integration, covering the agent's granted permissions. Default one hour. |
| **ledger** | bab's own tables: requests, decisions, grants, leases, events. The audit reads this, not OpenFGA. |

OpenFGA still answers the one question (does `agent:x` hold `p` on
`integration:y` right now). Everything around it is bab's service layer.

## Identity: how bab knows who is asking

An agent proves itself with the Kubernetes service account token its pod
already carries, projected with audience `bab`. bab verifies the JWT against
the cluster issuer, reads `system:serviceaccount:<ns>:<name>` from `sub`,
and maps it to `agent:<name>` through the topology the room pushes
(`PUT /topology`: each agent with its `namespace` and `service_account`). A
pod the topology does not name is refused; before any topology is pushed the
agent is its service account's name. No agent
secret, no agent-specific cloud principal, nothing to rotate. A person
calling the console routes come in through the console's own identity (the
room's IAP header) and are `user:<email>`.

## Data model

### Catalogue, generated per integration

Hand-written in increment one. Now each connected integration contributes a
permission tree, generated by `bab catalogue build` from two sources:

- cloud providers: the pack files in `cloud-access` (`packs/<cloud>.json`),
  one permission per service action family (`ec2.describe`, `logs.read`,
  `ce.read`), tiered by the pack
- other vendors: a permissions file bab carries per vendor
  (`vendors/<vendor>.yaml`), in the vendor's own grouping, with each
  permission tiered

```yaml
resources: [room, integration]
actions:
  - {name: datadog_monitors_read,  tier: read,    group: Monitors,  description: List and read monitors}
  - {name: datadog_monitors_write, tier: mutate,  group: Monitors,  description: Create, edit, mute monitors}
  - {name: aws_ec2_describe,       tier: read,    group: Compute,   description: Describe EC2 resources}
  - {name: aws_ecs_update_service, tier: mutate,  group: Compute,   description: Update an ECS service}
  - {name: github_repos_delete,    tier: destroy, group: Repos,     description: Delete a repository}
```

`group` is new and only for display (the expandable sections in the
console). The generator is unchanged in spirit: per permission `p` it emits
`p`, `p_gated`, `can_p`, `ceiling_p`, `ceiling_p_gated` on both levels.
Hundreds of permissions make a long model; OpenFGA is fine with that, and
the console never shows the model.

### Objects

`room:<name>` is the root; its `owner` is the admin team. `integration:<id>`
is one connected vendor or account (`integration:aws-prod`,
`integration:datadog`), child of the room. Agents do not appear in the tree;
they are subjects.

### Grants with expiry: OpenFGA conditions

OpenFGA has no tokens and no time-to-live, but it has **conditional
tuples**: a tuple can carry a condition, and every `check` passes context.
That is the whole mechanism for grant expiry.

```
type integration
  relations
    define datadog_monitors_read: [agent, agent with grant_window] or datadog_monitors_read from room

condition grant_window(current_time: timestamp, expires_at: timestamp) {
  current_time < expires_at
}
```

A grant tuple written with `expires_at` stops answering yes at that instant,
with no sweeper on the critical path. A nightly `bab sweep` deletes dead
tuples for tidiness. `[agent]` without a condition remains legal for
standing grants (read-tier inventory, by default).

Defaults for how long a grant lives, set per tier in the catalogue and
changed by an admin in the console:

| tier | grant validity | lease length |
|---|---|---|
| read | standing (no expiry) | 1 hour |
| mutate | 30 days, then re-request | 1 hour |
| destroy | 7 days, then re-request | 30 minutes |

### Ceiling = what the connection can do

The ceiling check from increment one (`ceiling.permitted`, at write time)
gets a real source. When a cloud account is connected, the role the account
owner created from packs is the most any agent in the room may hold there,
so the connection writes `room ceiling_p integration:<id>` for every
permission the role carries. A vendor connected with a read-only key gets
read-tier ceilings only. A request for anything above the ceiling is refused
at write time with the reason, before it reaches a reviewer.

### Approve verdict = just-in-time grant

Increment one's `approve` verdict was "post the plan, wait for a tick". It
now means: the agent has `p_gated`; a lease request for `p` creates a
one-hour grant request in the review queue; a reviewer's yes writes the
conditional tuple with `expires_at = now + 1 h`; the agent retries and gets
its lease. One mechanism serves standing permissions and break-glass.

## The lease

```
POST /leases                      bearer: projected service account token
{ "integration": "aws-prod", "permissions": ["aws_ec2_describe", "aws_logs_read"], "task": "incident 4312" }

200 { "lease_id": "...", "integration": "aws-prod",
      "granted": ["aws_ec2_describe", "aws_logs_read"], "refused": [],
      "credential": { ...vendor shape... }, "expires_at": "2026-10-27T15:04:00Z" }
```

1. Verify the token, resolve `agent:<name>`.
2. `BatchCheck` every requested permission with `current_time` in the
   context. `permissions` omitted means "everything I hold on this
   integration". Any `p_gated` hit turns into a review-queue request and the
   response says so.
3. Mint the credential through the integration's **minter**, scoped to the
   granted set, lifetime per tier.
4. Record the lease (agent, integration, permissions, task, issued,
   expires, OpenFGA consistency token) in the ledger.

### Minters: one per credential family, every one native

The cloud-agnostic part is the contract, not the credential. Each vendor in
the room's catalogue has a native short-lived path, and bab is the only
principal the vendor trusts.

| family | how bab mints | scoped to the granted set by | max life |
|---|---|---|---|
| AWS | `AssumeRoleWithWebIdentity` into the account's `KoboAccess-Role`, trust = bab's own cloud identity, `RoleSessionName=bab-<agent>` (that API takes no SourceIdentity) | a session policy built from the granted permissions | 1 h (role max) |
| Google Cloud (built, 0.4.15) | an access token for bab's own service account from the metadata server (the admin grants it the role pack on the project, folder or organization: no federation step), or `generateAccessToken` on the connection's `service_account` when one is named. With `BAB_GCP_AGENT_ACCOUNT` set, that request goes through the agent's own service account (`delegates`), so Cloud Audit Logs name the agent on every call; see below | bab's check only; the token carries the identity's roles (no session policy on this cloud), and the lease note says so | 1 h, or the metadata token's own expiry when shorter |
| Azure | workload identity federation client assertion | bab's check only | about 1 h |
| GitHub | App installation token | `permissions` and `repositories` narrowing on the token request | 1 h |
| Datadog | a **scoped application key**: one per agent, kept across leases, where bab has a key store; else one per lease, deleted at expiry | the key's own `scopes` | the lease is an hour; bab deletes the key when the agent's access changes |
| Fastly | create a token with `scope` and `expires_at` | the token's scope | expires itself |
| OAuth vendors (Atlassian, Okta, Wiz) | client-credentials access token with scopes | the scopes | vendor default, about 1 h |

The gateway's AWS handler (`liminal` 0.6, built this week) becomes
`bab/minters/aws.py` with the trust pointed at bab's identity instead of
the gateway's. The `cloud-access` module and the Connect AWS sheet change
one variable.

Two honest limits. A minted credential cannot be recalled before it
expires; the lease length is the revocation, with AWS's issue-time deny as
the emergency lever (`Revoke now` in the console). And where the cloud has
no per-session narrowing (Google Cloud, Azure), the granted set is enforced
by bab's verdict before minting, not by the vendor during the hour. The
console says which of the two applies to each integration; the Google Cloud
minter puts it in every lease's `note` so the console need not know.

### Datadog: a lease is an application key

Datadog has no short-lived tokens, but a *service account* can own *scoped
application keys*: a key carries any subset of the owner's permissions, is
created and deleted by API, and names itself in Datadog's audit log. So a
Datadog lease is a fresh application key on bab's service account, named
`bab-<agent>-<minute>`, scoped to the union of the granted permissions'
`extra.scopes` (the catalogue pins one or two Datadog permission names per
entry), handed to the agent as `{dd_api_key, dd_app_key, dd_site}` and
deleted when the lease ends. The hour is bab's, not Datadog's: a key never
expires on its own, so every lease request first deletes the keys of leases
that have run out, a revoke deletes the key the agent still holds, and the
sweep catches whatever is left.

bab holds three things for this, from the pod's environment: the service
account id (`DD_SERVICE_ACCOUNT_ID`), one organization API key
(`DD_API_KEY`), and one management application key owned by that service
account and scoped to `service_account_write` (`DD_MGMT_APP_KEY`). A key with
no scopes would carry everything the service account may do, so a lease whose
permissions name no scope is refused rather than minted wide. This is the
first service vendor where the vendor itself enforces the granted set during
the hour, as AWS does with the session policy.

Datadog refuses a new application key for a moment after it creates it
(0.7 to 3.1 seconds, measured from bab's pod; then 200 and never 403 again).
So the minter reads with the key before it hands it out, and returns once
Datadog answers 200. The read has to be one the key's own scopes allow, so
it is picked from a short table of pairings (`DD_KEY_READS` in
`bab/service/minters.py`): monitors, events, a metric query. A key that
carries none of those scopes is held for a fixed 2.5 seconds instead. The
wait is bounded at 6 seconds, and it fails open: a key Datadog has not
accepted by then is handed out with a note on the lease, because a lease
that works a second late is better than no lease. A caller's lease request
therefore takes 1 to 3 seconds longer on a mint, and its timeout has to
allow for that.

#### The key outlives the lease, where there is somewhere to keep it

A key an hour per agent is a key made and a key deleted in Datadog's audit
trail every hour for every agent, and a message to the service account's
owner each time. Nothing about the hour needed that: Datadog's keys do not
expire, so the hour was always bab's lease, never the key's.

So when bab has a key store (`bab/service/keys.py`), an agent has one key
per Datadog connection, named `bab-<agent>`, and a lease on everything the
agent holds hands out that same key (`DatadogMinter.mint_standing`). The
lease is unchanged: an hour, a row in the ledger, asked for again when it
runs out. What changes is when the key is deleted:

- a permission is approved, or a grant is revoked: `end_live` calls the
  minter's `drop`, the key is deleted at once, and the next lease makes one
  with the new scopes;
- a grant lapses by its date: the next lease carries fewer scopes than the
  key does, so the old key is deleted and a new one made; when nothing is
  left, the refusal deletes it. An agent that has stopped asking tells
  nobody, so every kept key is also checked against the ledger
  (`settle_kept`: after any lease is given, at most every five minutes,
  in a session of its own, and on `/sweep`), and one that carries a scope
  its agent no longer holds is deleted. The check takes the key's lock, so
  it deletes the key it judged and never one a lease made meanwhile;
- the agent is removed, or Datadog is disconnected: deleted with the
  grants. A disconnect deletes every kept key on the connection, whether or
  not its agent still holds a grant there.

A lease ending is not on that list. `end` knows a kept key from a key made
for one lease and leaves the first alone. A lease that names its
permissions still gets a key of its own (`mint`), so asking for less never
replaces the key the gateway is using.

A key Datadog refuses to delete when access changes is marked and never
handed out again. The same check against the ledger tries the delete again,
and so does the agent's next lease, which fails if it cannot.

A lease reads the grants and then mints, and a revoke that lands between
the two finds no lease to end. For a key made per lease that was an hour of
a scope just taken back; for a kept key it would be for as long as the key
is kept. An approval in the same moment takes nothing away but deletes the
kept key, so the lease would hand out a key Datadog no longer has. So
`lease_for` records the lease first and then asks again, for every vendor:
the store whether the grants still hold, and the minter (`holds`) whether
the credential is still one to hand out; until both answer, the cached
credential is not served to anyone else. A change after that point finds
the recorded lease and ends it. A change before it is caught by the second
asking: the lease is ended at once, a kept key dropped on a revoke, and the
lease refused with 409 and "ask again".

The store is the room's secret store, written through sero's machine lane
as bab's own identity and read back from a Secret sero delivers to bab's
namespace: sero never returns a value. bab needs the mount only after a
restart, and it lags a write by about a minute.

One rule covers what a restart has to get right: an agent never has two
kept keys. Only its record knows a kept key's id, so a second key made
beside it would leave the first in Datadog for good. Datadog enforces the
same thing from its side: a service account has one application key per
name, and a second create under `bab-<agent>` answers 409 (measured). So
`mint_standing` makes a kept key only when it knows none is standing, and
otherwise gives the lease a key of its own (`mint`), deleted with the
lease, saying why in the log once:

- the mount does not show a record the store holds (asked by name; sero
  answers names, never values): the restart came before the delivery, or
  the delivery was refused. bab asks for the delivery again (at most once a
  minute), and the kept key is used again once the mount shows it. A revoke
  that finds only the store's record says so in the log, and the ledger
  check deletes the key once the mount shows it;
- the store does not answer;
- the mount shows a key and Datadog will not say whether it still has it
  (asked by id with the management key: 200 keeps it, 404 replaces it,
  anything else is no answer);
- Datadog refuses the name: a newer kept key the mount has not shown yet,
  or a key someone else made. The store's record is not overwritten.

A key the store refused is one lease's key and is deleted with it. A key
recorded on another service account (the connection was moved) is deleted
there while the management key can still reach it, and named in the log
when it cannot. An agent with a dot in its name has no kept key, so
`<integration>.<agent>` splits one way.

Without a key store bab keeps no key past its lease. The ledger does not
hold secrets, and a key kept only in memory would be remade for every agent
at every restart with the old ones left in Datadog.

Limits. One bab process is assumed, as the lease cache already assumes. The
check against the ledger runs when some lease is given or on a sweep,
so a room with no lease traffic at all keeps a lapsed grant's key until
the next of either. A lease that ends in the minute after a restart, before
the mount shows the kept key it carried, deletes that key, and the next
lease makes another. A key under an agent's kept name that bab does not
hold is not deleted by name (two rooms may mint on one service account):
a person deletes it, and until then that agent gets a key per lease.

The tool gateway, not the agent, is what reaches Datadog today; it leases
through `POST /leases/for-agent` with its own pod identity, naming the agent
whose call it is serving. The checks are the agent's; the row says `via:
gateway`.


### Google Cloud: the agent in the cloud's own log

A token bab asks for directly is logged by Google as the connection's service
account, with bab as the one who asked. Which agent it was for is in bab's
ledger only. `BAB_GCP_AGENT_ACCOUNT` closes that: it is a pattern for each
agent's own service account, with `{agent}` standing for the name
(`agent-{agent}@<project>.iam.gserviceaccount.com`). With it set, a lease is
asked for as a chain, bab to the agent's account to the account the token is
for, and Google records the agent's account in `serviceAccountDelegationInfo`
on every call the token makes. The account the token is for is the connection's
`service_account`, or bab's own where the connection names none: bab, through
the agent, back to bab, which carries the same roles as bab's own token.

The chain needs two grants of Service Account Token Creator: bab's identity on
the agent's account, and the agent's account (or a group it is in) on the
account the token is for: the connection's, or bab's own. Nothing may run as the agent's account. It is a name in a
chain, and a workload that ran as it could ask for the connection's token
itself, with no grant and no lease. The room keeps that true: an agent's pod is
granted what it needs on its Kubernetes identity directly.

Where Google refuses the chain (the agent's account is not a link yet, or the
grant is minutes old) bab asks directly, as before, and the lease note says the
cloud's log does not name the agent. A new grant took about a minute and a half
to count when this was first run against Google (2026-11-24).

## Runtime

The agent runtime's integration tools stop reading a mounted secret and ask
a **credential provider** that calls `POST /leases` the first time a task
touches an integration, caches the credential until a minute before
`expires_at`, and asks again after. A `refused` permission surfaces to the
model as the tool result ("you do not hold aws_ecs_update_service; ask
your owner to request it"), so the model does not retry. A pending gated
request surfaces as "waiting for approval", as gated tools do today.

Degraded: if OpenFGA or bab is unreachable, no new lease is minted (fail
closed). Leases already held keep working until they expire, which is the
only buffer and is bounded by the lease length. This answers issue #8,
question 4: on the tool path, deny.

## Ledger and audit

Postgres tables in bab's own database (next to OpenFGA's, on the room's
instance):

| table | one row per |
|---|---|
| `requests` | a set of permissions asked for one agent on one integration: who asked, when, note, status |
| `decisions` | a reviewer's verdict on a request: who, when, approve or deny, reason |
| `grants` | an active permission with its expiry and the tuple it wrote |
| `leases` | a minted credential: agent, integration, permissions, task, issued, expires, consistency token |
| `events` | everything else bab did (sweeps, revokes, minter failures) |

Per-call activity lives with the vendor and names the agent: CloudTrail
rows carry the session name `bab-<agent>` in the assumed-role ARN, GitHub audit carries the installation token's
actor, Datadog audit carries the key's name, which carries the agent's. The console's Activity view
reads bab's leases and links to the vendor's log for the window. bab does
not proxy calls and does not try to see them.

## API

| Method | Path | Who | Purpose |
|---|---|---|---|
| POST | `/leases` | agent | mint a lease (above) |
| GET | `/leases?agent=&integration=&since=` | console | activity |
| POST | `/requests` | console (owner) | ask for permissions for an agent |
| GET | `/requests?status=pending` | console (reviewer) | the review queue |
| POST | `/requests/decide` | console (reviewer) | bulk approve or deny, with a reason |
| GET | `/agents/{agent}/grants` | console | what the agent holds, with expiries |
| DELETE | `/grants/{id}` | console (admin) | revoke now; optionally invalidate open AWS sessions |
| GET | `/catalogue/{integration}` | console | the permission tree for the picker |
| POST | `/check` | anyone with a token | increment one's verdict, kept |
| POST | `/sweep` | cron | delete expired tuples and vendor-side keys |

Reviewers are the room's admin team or the security team; the destroy tier
requires the security team. Both sets are tuples (`team member`), so the
console never hard-codes them.

## What this replaces

- Gateway grant files as the permission authority. The gateway, where it
  stays for MCP vendor tools, asks `/check` at dispatch and owns no grants.
- The console's one-row-per-agent-per-vendor lanes. A lane becomes a grant
  set with expiries.
- The "profile" layer proposed for cloud lanes: the approved permission set
  is the profile, and the session policy is built from it at lease time.
- Mounted vendor keys in agent pods, once the runtime's credential provider
  ships. Until then an integration can run both ways during the move.

## Increments

2. **Model and catalogue**: `group` in the catalogue; conditions in the
   generator (`agent with grant_window`); `room` and `integration` levels;
   `bab catalogue build` from pack files and vendor permission files;
   tuple writer with the ceiling check wired in; `fga model test` covers a
   window that has passed.
3. **Service**: bab becomes an HTTP service: token verification, ledger
   tables and migrations, `/requests`, `/decide`, `/grants`, `/leases`,
   `/sweep`; minters for AWS first, then GitHub and Datadog, then Google
   Cloud and Azure.
4. **Deploy**: OpenFGA and bab on the dev cluster, databases on the room's
   instance, bab's cloud identity bound; the account role's trust moves to
   it; nightly sweep CronJob.
5. **Runtime**: the credential provider in the agent runtime; one agent
   moves off its mounted key as the proof.
6. **Console**: the permissions step at creation, the review queue with
   bulk decide, grants with expiry on the agent page, Activity from the
   ledger. Specified on the console side; this document is the contract.

## Open, with the default we will take unless told otherwise

- Grant validity per tier: the table above.
- A lease request without `permissions` gets everything the agent holds on
  that integration. Simpler for the model, wider than the task needs.
- Whether a human can be the subject of a lease (a person borrowing an
  agent's access). No: people use their own access; bab leases to agents.
